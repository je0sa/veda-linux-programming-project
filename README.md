# 🚀 Raspberry Pi 원격 하드웨어 제어 데몬 서버 시스템

![Linux](https://img.shields.io/badge/Linux-FCC624?style=for-the-badge&logo=linux&logoColor=black)
![C](https://img.shields.io/badge/C-00599C?style=for-the-badge&logo=c&logoColor=white)
![Raspberry Pi](https://img.shields.io/badge/Raspberry%20Pi-A22846?style=for-the-badge&logo=Raspberry%20Pi&logoColor=white)

**Ubuntu(클라이언트)와 Raspberry Pi 4(서버) 간의 TCP/IP 소켓 통신을 이용하여 원격으로 임베디드 하드웨어(LED, CDS, 7-Segment, Buzzer)를 제어하는 시스템 프로그래밍 프로젝트입니다.** 단순한 하드웨어 제어를 넘어 **동적 공유 라이브러리(`dlopen`), 시스템 데몬(Daemon Process), 멀티스레딩(Multi-threading), I/O 멀티플렉싱(`select`), 분할 컴파일 아키텍처** 등 리눅스 시스템 프로그래밍의 핵심 기술들을 적용하여 서버의 안정성과 범용성을 극대화했습니다.

<br>

## 1. 프로젝트 개요

### 1.1 시스템 구성 및 개발 환경
* **서버 (Target Board)**
  * **하드웨어:** Raspberry Pi 4
  * **운영체제:** Linux (Raspberry Pi OS)
  * **실행 형태:** 시스템 백그라운드에서 상시 동작하며 시스템 로그(`syslog`)를 남기는 데몬 프로세스
* **클라이언트 (Host PC)**
  * **운영체제:** Ubuntu Linux
  * **특징:** `select()` 기반의 I/O 멀티플렉싱 넌블로킹 통신 및 시그널 가드(SIGINT 제외 블로킹) 적용
* **빌드 및 배포 시스템**
  * 모듈형 분할 `Makefile` 구성
  * `scp.sh` 쉘 스크립트를 통한 원클릭 크로스 컴파일 및 원격 배포 자동화

### 1.2 제어 대상 장치 (Target Devices)
* **LED:** PWM 제어를 통한 원격 On/Off 및 밝기 조절(HIGH/MID/LOW)
* **조도 센서 (CDS):** I2C 통신 기반 아날로그 값 실시간 모니터링 및 임계값에 따른 조명 자동 제어 연동
* **7-세그먼트:** 시작 숫자(0~9) 입력 시 카운트다운 타이머 구동 (0 도달 시 부저 연동)
* **부저 (Buzzer):** 스레드 동시성(`volatile` 플래그) 제어를 통한 배경 음악 재생 및 즉각 종료 제어

## 3. 실행 방법

프로젝트 최상위 디렉토리에서 자동화 스크립트를 통해 빌드 및 라즈베리파이 배포를 진행합니다.

> ⚠️ **주의 사항:** `scp.sh` 스크립트를 실행하기 전에 파일 내부의 서버 접속 정보(사용자명, IP)를 본인의 라즈베리파이 환경에 맞게 반드시 수정해야 합니다.

```bash
# scp.sh 수정 예시
RPI_USER="jjhword"                     # 라즈베리파이 사용자 계정
RPI_IP="100.94.125.69"                 # 라즈베리파이 IP 주소
TARGET_DIR="/home/jjhword/rpi_project" # 라즈베리파이 내부에 저장될 폴더 경로
```

**실행 순서:**
```bash
# 1. 자동 빌드 및 서버 배포 스크립트 실행 (Ubuntu 프로젝트 최상위 폴더)
$ ./scp.sh

# 2. 배포된 디렉토리에서 서버 데몬 가동 (Raspberry Pi)
$ ./server
# (실행 즉시 백그라운드로 전환되며 터미널 제어권을 반환합니다.)
# 로그 확인: sudo journalctl -f -t ./server

# 3. 프로젝트 루트 디렉터리에서 클라이언트 실행 (Ubuntu)
$ ./bin/client <라즈베리파이_IP>
```

### 4.2 주요 아키텍처 특징
* **동적 공유 라이브러리 아키텍처:** 서버(`server.c`) 컴파일 시점에 하드웨어 코드(`wiringPi` 등)를 종속시키지 않고, 클라이언트의 명령이 들어올 때 워커 스레드 내부에서 `dlopen`을 통해 `libdevice.so`를 런타임에 동적으로 바인딩합니다. 이를 통해 하드웨어 제어 로직이 수정되어도 서버 본체는 재컴파일할 필요가 없는 높은 유연성을 확보했습니다.
* **멀티스레드 기반 비동기 제어:** 메인 서버 프로세스는 다중 클라이언트의 `accept`만을 담당하고, 통신 및 파싱 처리는 `pthread`로 분리하여 병목을 방지했습니다. 또한 부저의 음악 재생처럼 시간이 걸리는 하드웨어 작업은 스레드 단위로 제어하여 시스템 응답성을 유지합니다.

## 5. 🛠️ 핵심 트러블 슈팅 (Trouble Shooting)
프로젝트를 진행하며 겪었던 주요 시스템적 이슈와 해결 과정입니다.

### 💡 Issue 1: `select()` 멀티플렉싱 중 UI 프롬프트 출력 버퍼링 현상
* **문제:** 클라이언트에서 키보드 입력과 서버 소켓을 동시에 감시하기 위해 `select()` 대기 상태로 진입하기 전, 메뉴판 출력을 위한 `printf()` 문자열이 모니터에 즉시 출력되지 않고 사용자가 키보드 입력을 발생시켜야만 화면에 지연 출력되는 현상 발생.
* **원인:** 리눅스 표준 입출력(`stdout`)은 개행 문자(`\n`) 단위로 작동하는 라인 버퍼링(Line Buffering)을 사용함. 메뉴 출력문 끝에 `\n`이 없어 출력 버퍼에 갇힌 상태로 `select()` 함수가 블로킹 상태로 들어가 버림.
* **해결:** `select()` 진입 직전에 `fflush(stdout);`을 명시적으로 호출하여 갇혀있는 출력 버퍼를 모니터 화면으로 강제 방출시킴으로써 즉각적인 UI 반응성을 확보.

### 💡 Issue 2: 분할 컴파일 아키텍처의 링커(Linker) 충돌
* **문제:** 최상위 `Makefile`을 통해 서브 디렉토리를 분할 컴파일하는 과정에서, `server.c` 내부에서 하드웨어 초기화 함수인 `device_init()`을 호출하자 `undefined reference` 에러가 발생하며 빌드 실패.
* **원인:** 서버를 동적 로딩(`dlopen`) 아키텍처로 설계하여 `server/Makefile`에 라이브러리를 직접 링크(`-ldevice`)하지 않았으나, 소스코드에서는 일반적인 정적 함수처럼 호출하여 링커가 해당 함수의 실제 구현부를 찾지 못함.
* **해결:** `main` 함수 초입의 초기화 함수 호출부 역시, 런타임에 `dlopen`을 통해 핸들을 얻어오고 함수 포인터로 실행하도록 코드 구조를 완벽하게 동적 로딩 규격으로 통일하여 링커 에러를 원천 우회함.

### 💡 Issue 3: 시스템 데몬의 경로 유실(`chdir`)과 `dlopen` 딜레마
* **문제:** Stevens의 정석 데몬 패턴인 `become_daemon`을 적용하여 서버를 데몬화하는 과정에서 정규 패턴인 `chdir("/")`를 수행하자, 하위 스레드들이 `dlopen("./libdevice.so")`을 호출할 때 라이브러리를 찾지 못해 모든 장치 제어가 먹통이 되는 치명적 버그 발생. 작업 디렉토리가 루트(`/`)로 변경되어 상대 경로 탐색에 실패함.
* **시도:** 이를 해결하기 위해 `getcwd()`를 활용한 동적 경로 추적이나, 외부 배포 스크립트를 통해 라이브러리를 리눅스 전역 공유 폴더(`/usr/lib`)로 강제 매립하는 `sudo ldconfig` 방식을 설계함.
* **🚀 최종 해결 (발상의 전환 - KISS 원칙):** "과연 이 임베디드 프로젝트 환경에서 `chdir("/")`가 반드시 필요한가?"에 대한 근본적인 의문을 제기함.
  * 서버에서 `chdir("/")`를 하는 주된 이유는 USB 등 임시 마운트된 볼륨에서 데몬이 실행될 경우 해당 디렉토리가 락업되어 언마운트를 방해하는 현상을 막기 위함임.
  * 그러나 본 프로젝트는 라즈베리파이 내부 고정 저장소에 배포되어 구동되므로, 작업 경로를 강제로 루트로 이탈시킬 실질적 필요성이 없다고 판단함.
  * 결과적으로 데몬화 함수 내부에서 **`chdir("/")` 코드 단 한 줄을 과감히 삭제함**. 이를 통해 복잡한 권한 제어 스크립트나 경로 래핑 없이도 데몬 프로세스가 실행 폴더 위치를 그대로 유지하게 되었고, `./libdevice.so`를 정상적으로 로드 해내는 해결책을 도출.

## 7. 🔌 하드웨어 핀 맵 및 GPIO 설정 가이드 (Pinmap Configuration)

본 프로젝트는 라즈베리파이의 GPIO 제어를 위해 **wiringPi(wPi)** 핀 번호 체계를 사용합니다. 하드웨어 결선 시 아래의 핀 맵 가이드를 참고하여 회로를 구성해 주십시오.

### 7.1 프로젝트 기본 핀 매핑표
코드에 기본적으로 세팅된 장치별 핀 번호와 물리적(Physical) 핀 위치입니다.

| 모듈 (Device) | wiringPi 핀 번호 | Physical 핀 번호 | BCM 핀 번호 | 비고 / 통신 방식 |
| :--- | :---: | :---: | :---: | :--- |
| **LED** | `wPi 1` | Pin 12 | 18 | PWM (밝기 조절용) |
| **Buzzer** | `wPi 6` | Pin 22 | 25 | softTone (주파수 출력) |
| **CDS (조도센서)** | `wPi 8, 9` | Pin 3, 5 | 2, 3 | I2C 통신 (SDA.1, SCL.1) |
| **7-Segment (A~G)** | `wPi 21~25, 27, 28` | Pin 29, 31, 33, 35, 37, 36, 38 | 5, 6, 13, 19, 26, 27, 28 | OUTPUT (디지털 출력) |

### 7.2 터미널에서 GPIO 핀 상태 확인하기 (Bash 가이드)
회로 연결 전후로 핀의 상태나 모드(IN/OUT/ALT)를 확인하려면 라즈베리파이 터미널에서 아래 명령어를 실행하세요.

```bash
# 라즈베리파이 GPIO 전체 핀 맵 및 현재 상태 출력
$ gpio readall
```

### 7.3 사용자 맞춤형 핀 번호 변경 방법
만약 사용자의 라즈베리파이 하드웨어 결선 환경에 맞춰 다른 핀으로 변경하고 싶다면, 관련 소스코드의 매크로 상수 및 전역 배열 변수를 수정한 후 최상위 디렉토리에서 스크립트(`./scp.sh`)를 가동해 재컴파일 및 자동 배포를 진행하면 됩니다.

**1. LED 및 부저(Buzzer) 매크로 핀 변경**
`device/src/setup.c` 파일 상단의 매크로 정의 값을 수정합니다.
```c
// device/src/setup.c
#define LED  1    // wPi 1 (기본값) -> 원하는 사양의 wPi 번호로 변경
#define SPKR 6    // wPi 6 (기본값) -> 원하는 사양의 wPi 번호로 변경
```
